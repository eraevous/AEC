## User Scenarios & Testing *(mandatory)*

### User Story 1 - Start AEC in an existing repository (Priority: P1)

A developer (Zach, about to overhaul Data-Guide) runs one command in a repository that has never used AEC, Spec Kit or not, and gets a working AEC setup: a records file with an authority and a purpose stub that is clearly marked as a stub, a first structural snapshot of the code, and ready-to-copy hook and CI snippets. Running the checks immediately afterwards passes.

**Why this priority**: nothing else can be adopted until the repository has AEC in it, and today that is done by hand.

**Independent Test**: run it in a fresh copy of a plain repository and in a Spec Kit repository; the checks pass on both; running it a second time changes nothing.

**Acceptance Scenarios**:

1. **Given** a repository with no `.aec/`, **When** the developer initializes AEC, **Then** a records file, a structural snapshot and snippet files exist, and the record checks report 0 errors.
2. **Given** an initialized repository with edited records, **When** initialization is run again, **Then** no existing file is overwritten and the developer is told what was kept.
3. **Given** a Spec Kit repository, **When** initialization runs, **Then** it says how to register the AEC Spec Kit extension, without editing Spec Kit files.

---

### User Story 2 - Bring old purpose files in without promoting them (Priority: P1)

Data-Guide already has 25 Codex++ `.purpose.md` files written in 2025, many generated by a model and never verified, describing a codebase that has since drifted. The developer imports them so their claims become records AEC can reason about, while keeping three things distinct: what the file claimed, what the code currently does, and what the owner wants now.

**Why this priority**: it removes most of the authoring cost of adopting AEC on a repo with history, and it is the first place old claims meet the actual code.

**Independent Test**: import the purpose files of a fixture repository; every imported record is provisional and carries the source file and its content hash; declared-vs-observed differences are listed; nothing imported can satisfy an authority check.

**Acceptance Scenarios**:

1. **Given** a purpose file naming its source files and callers, **When** imported, **Then** a provisional record holds its intent text verbatim with provenance (path, content hash, its own `generated`/`verified` flags), and links to the code it describes when that code exists in the snapshot.
2. **Given** a purpose file that declares callers which do not actually call the module (or misses callers that do), **When** imported, **Then** the difference is reported as a finding, not silently corrected.
3. **Given** a purpose file naming a source file that no longer exists, **When** imported, **Then** the record is still created and the missing file is reported.
4. **Given** imported records, **When** any of them is used as the basis of an accepted decision, **Then** the checks still require a governing authority; import grants none.
5. **Given** the same purpose files imported twice, **Then** no duplicate records are created; a changed file produces a new version.

### User Story 3 - Catch "it passes, therefore it works" (Priority: P2)

A record claims the system achieves its purpose (an outcome), but the only supporting evidence is that the implementation conforms to its contract (tests pass, reports render). The checks warn that the outcome claim rests only on conformance evidence. The warning says the inference is unsupported, not that the claim is false. When outcome evidence exists, the check passes.

**Why this priority**: Kate's acceptance test for AEC: "a system can correctly perform every operation it was instructed to perform while becoming progressively less capable of accomplishing the purpose for which it was built." This is the single check most distinctive to AEC.

**Independent Test**: three fixtures: an outcome claim supported only by conformance evidence (warns); the same claim with outcome evidence added (passes); a requirement-satisfaction claim supported by conformance evidence (passes; decoy).

**Acceptance Scenarios**:

1. **Given** a purpose-outcome claim whose only supporting evidence is contract conformance, **When** checked, **Then** a warning names the claim and the evidence and says the inference is unsupported.
2. **Given** that claim plus one outcome observation, **When** checked, **Then** no warning.
3. **Given** a requirement-satisfaction claim supported by contract conformance, **When** checked, **Then** no warning.
4. **Given** an unknown evidence kind or claim category, **When** checked, **Then** it is reported as an error.

---

### User Story 4 - Evidence that may no longer apply (Priority: P3)

Evidence was observed against specific code (a test run, a profiled report). When that code changes, the evidence is flagged for an applicability review and the claims it supports need review. The original observation is kept; nothing is invalidated.

**Why this priority**: closes the "valid evidence that no longer applies" gap with the smallest addition; Kate asked that it stay narrow.

**Independent Test**: evidence observed on a function; change the function body → evidence needs review; change an unrelated function → nothing (decoy); delete the function → still only review, never unjustified.

**Acceptance Scenarios**:

1. **Given** evidence observed on a code symbol, **When** that symbol's body changes, **Then** the evidence and the claims it supports are flagged for review, and no status worse than review is produced by the code change alone.
2. **Given** a change to unrelated code, **Then** nothing is flagged.

### Edge Cases

- Purpose files that are templates (placeholder values like `<file1.py>`) are skipped and reported, not imported as claims.
- Purpose files whose source is a notebook or a document (not Python) are imported with no code link and say so.
- A bare file name in a purpose file that matches several files in the repo is reported as ambiguous; no link is guessed.
- Initialization in a directory that is not a repository still works (AEC does not require git).
- A purpose file with no recognisable header fields is imported as text only, with a finding.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Initialization MUST create, only where absent, a records file containing an authority record for the owner and a provisional purpose stub, a structural snapshot, and hook and CI snippet files; it MUST NOT overwrite existing files and MUST report what it created and kept.
- **FR-002**: Initialization MUST work with or without Spec Kit and MUST NOT modify Spec Kit files; with Spec Kit present it prints the extension install command.
- **FR-003**: Import MUST create one provisional record per purpose file, preserving the intent text verbatim, the file path, a content hash, and the file's own generated/verified flags.
- **FR-004**: Imported records MUST never be authorities, never committed, and never satisfy an authority check (`AEC-R1@1`).
- **FR-005**: Import MUST link records to code symbols only when the named source resolves unambiguously in the structural snapshot; otherwise it reports why no link was made.
- **FR-006**: Import MUST report declared-vs-observed differences for declared callers, comparing them with the modules that actually import or call the described module.
- **FR-007**: Import MUST be idempotent: unchanged files create no new records; changed files create a new version of the same record id.
- **FR-008**: Evidence records MAY declare a kind from {contract_conformance, behavioral_observation, outcome_observation}; claims MAY declare a category from {requirement_satisfaction, purpose_outcome}; unknown values are errors.
- **FR-009**: The checks MUST warn when a purpose_outcome claim has supporting evidence and all of it is contract_conformance; the warning MUST describe an unsupported inference and MUST NOT mark the claim false or unjustified.
- **FR-010**: Evidence MAY declare that it was observed on a code symbol; a change to or removal of that symbol MUST flag the evidence for review and propagate review to what it supports, and MUST NOT by itself produce `unjustified`.
- **FR-011**: The governing invariant "a code dependency is not a justificatory dependency" MUST be stated in the vocabulary document, and every code-derived change MUST produce review statuses only, except where a claim or evidence record has an explicit `depends_on` link to code that was deleted. Obligations (requirements, purposes, criteria) are never invalidated by code: deleting their implementation makes their recorded satisfaction unjustified and the obligation `needs_review` (amended after Kate's round-4 review; changes feature 001's behaviour for requirements).
- **FR-013** *(added at converge)*: Imports written relative to a source directory on the import path MUST resolve to the module that exists, only when unambiguous, never for standard-library names, and the snapshot MUST say which source roots it used.
- **FR-012**: All new behaviour MUST run in CI on this repository and ship with a violating fixture and a clean decoy (Constitution III).

### Key Entities

- **Imported purpose record**: provisional record derived from a `.purpose.md` file; carries source path, content hash, original flags, verbatim intent; links to code where resolvable.
- **Import finding**: a declared-vs-observed difference, an unresolved source, a template file, or an ambiguous name.
- **Evidence kind / claim category**: small enumerations that let the checks tell conformance from outcome.
- **Observation link**: evidence → code symbol it was observed on.

## Success Criteria *(mandatory)*

- **SC-001**: On a copy of Data-Guide, initialization plus import of all its purpose files completes in under 10 seconds and the checks then report 0 errors.
- **SC-002**: 100% of imported records are provisional and carry provenance; 0 imported records can satisfy an authority check.
- **SC-003**: On Data-Guide, every declared caller that does not match the code is reported (verified by hand on at least 5 files).
- **SC-004**: The outcome-sufficiency check flags the violating fixture, passes the sufficient fixture and the decoy: 3/3.
- **SC-005**: A clean change (unrelated code edit) produces 0 findings from code-impact (no spurious objections).
- **SC-006**: A relevant code change produces review statuses only, never `unjustified`, for observed-on evidence.

## Assumptions

- Purpose files follow the Codex++ `@ai-*` header style (Data-Guide's do); other formats are imported as text only.
- "Owner" for the authority stub is taken from a command-line value or the git user name; it is a stub the owner confirms.
- Blind historical cases (Kate's F) and the Spec Kit replay (G, feature 003) are out of scope here.
- The pinned Spec Kit version stays 1.2.3.
